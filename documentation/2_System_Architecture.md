# 2. System Architecture

The project follows a layered architecture, which separates concerns and improves modularity. The code is organized into several directories within the `main` folder, each with a specific responsibility.

```
main/
├── backend/      # Core business logic and data management
├── frontend/     # UI logic, screen transitions, and data binding
├── hardware/     # Hardware Abstraction Layer (HAL)
├── ui/           # LVGL screen definitions, widgets, and styles
├── main.c        # Main application entry point
└── ...
```

## 2.1. `main`

*   **`main.c`**: This is the entry point of the application (`app_main`). It is responsible for initializing the system, including hardware drivers, backend services, and the UI manager. After initialization, it enters a background loop, while the UI and other tasks run.

## 2.2. `backend`

The backend is responsible for the core application logic and data handling, completely independent of the UI.

*   **`data_model.c` / `.h`**: Defines and manages the central data structures of the application. This includes:
    *   `NozzleData`: Information about each fuel nozzle (e.g., product name, price).
    *   `TransactionData`: State of the current transaction (e.g., selected nozzle, dispense mode, value, payment method).
*   **`system_config.c` / `.h`**: Handles the loading and saving of system-wide configurations, such as nozzle data from non-volatile storage.

## 2.3. `frontend`

The frontend acts as a bridge between the backend (data) and the UI (presentation).

*   **`ui_manager.c` / `.h`**: This is the heart of the UI logic. It is responsible for:
    *   **Screen Transitions:** Contains functions like `transition_to_numpad()`, `transition_to_confirm()`, etc., which handle the logic of moving between different screens.
    *   **Data Binding:** Updates UI elements with data from the backend. For example, it populates the confirmation screen with the selected nozzle, mode, and value.
    *   **UI Initialization:** Sets up the initial state of the UI when the application starts.

## 2.4. `ui`

This directory contains all the code directly related to the LVGL user interface. A significant portion of this code is auto-generated by EEZ Studio.

*   **`screens.c` / `.h`**: Contains the definition and layout of all the screens and their widgets (buttons, labels, text areas, etc.).
*   **`actions_impl.c` / `.h`**: Implements the event handlers for UI interactions. When a user presses a button, the corresponding function in this file is executed. For example, `action_mode_amount()` is called when the "By Amount" button is pressed.
*   **`assets`**: Other files in this directory define UI assets like fonts (`fonts.h`), images (`images.c`/`.h`), and styles (`styles.c`/`.h`).

## 2.5. `hardware`

The Hardware Abstraction Layer (HAL) provides a high-level API for interacting with the hardware components, isolating the rest of the application from low-level hardware details.

*   **`hardware_api.c` / `.h`**: Provides simple functions like `hardware_init_all()` to initialize all necessary hardware.
*   **Driver-specific code**: (e.g., `waveshare_rgb_lcd_port.c`) This is where the low-level communication with specific hardware components (like the LCD and touch controller) happens.
